# 0001 — 동기화 코드를 6자리로 유지하고 추측 위험을 감수한다

## 상황

새 동기화 코드를 만들 때 6자리 난수를 뽑아 확인 없이 클라우드에 썼다. 겹치면 그 코드를 쓰던
사람의 가계부가 통째로 사라졌다. 반대 방향으로도, 6자리는 90만 가지뿐이라 찍어 맞히면 남의
가계부를 읽고 쓸 수 있다. 서버 쪽 접근 규칙이 없어 코드가 접근 수단 전부다.

## 결정

**자리수는 6자리로 유지한다.** 대신 발급 전에 그 코드가 이미 쓰이고 있는지 확인하고, 쓰이고
있으면 다른 코드를 뽑는다(최대 10회). 확인 자체가 실패하면 아무것도 쓰지 않는다.

## 고르지 않은 것

- **8자리 또는 10자리로 늘리기** — 찍어 맞힐 확률이 100배·10000배 낮아진다. 사용자가 거절했다:
  다른 기기에 손으로 입력하는 것이 이 기능의 전부이고, 6자리가 입력하기 편한 한계라고 봤다.
- **문자를 섞기** — 같은 자리수로 경우의 수를 늘릴 수 있지만 입력이 더 번거로워진다. 같은 이유로
  제외.
- **삽입으로 바꿔 데이터베이스가 중복을 막게 하기** — `upsert` 대신 고유 제약 + `insert`를 쓰면
  경합까지 완전히 막힌다. 데이터베이스 쪽 스키마 변경이 필요하고 오류 처리도 달라져 이번 범위
  밖으로 뒀다.

## 결과 / 제약

- **남의 데이터를 덮어쓰는 사고는 막혔다.** 확인되지 않은 코드로는 쓰지 않는다.
- **추측당할 위험은 그대로 남는다.** 이것은 모르고 남긴 구멍이 아니라 알고 받아들인 위험이다.
  "코드가 짧아 위험하다"는 이유로 자리수를 늘리면 사용자가 내린 결정을 되돌리는 것이 된다.
- **경합은 여전히 가능하다.** 두 기기가 같은 순간에 같은 코드로 확인을 통과하면 나중에 쓴 쪽이
  이긴다.
- 실질적인 접근 통제를 붙이려면 Supabase 쪽 규칙을 손봐야 하고, 그것은 이 저장소 밖이다.
